# Internationalization (i18n) Guide

How bilingual (Bulgarian / English) content works in the **Личностно овластяване** web app, plus 5-language dashboard editing with DeepL auto-translation.

---

## Overview

The app uses a **lightweight, custom i18n system** — no external library. All UI strings are defined in a single dictionary file, and a helper function retrieves the correct translation based on the active locale.

This approach was chosen because:
- The **public site** needs only **2 languages** (BG/EN — no complex pluralization or ICU rules)
- Keeps the bundle small (no i18n runtime)
- Simple to maintain — all strings in one place
- Sufficient for a content-driven marketing site

### Dashboard: 5-language support + DeepL

The dashboard **Website tab** (`components/dashboard/WebsiteTab.tsx`) supports **5 languages**: BG, EN, ES, IT, DE. Bulgarian is the source language; the other four are populated via **DeepL auto-translation**.

- Locale type: `"bg" | "en" | "es" | "it" | "de"`
- Translate button in the sticky top bar: `BG → <selected locale>` calls `/api/translate` (requires `DEEPL_API_KEY` env var)
- Each multilingual field (`Multilingual = Partial<Record<DashboardLocale, string>>`) renders only the active locale's value, switched via the language switcher
- Homepage content is persisted via `/api/dashboard/homepage` (GET/PUT)

## The i18n File

**Location:** [`lib/i18n.ts`](../lib/i18n.ts)

### Structure

```typescript
// Locale types
export type Locale = "bg" | "en";
export const locales: Locale[] = ["bg", "en"];
export const defaultLocale: Locale = "bg";

// Translation dictionary — every string has both BG and EN
export const t: Dict = {
  nav_home: { bg: "Начало", en: "Home" },
  nav_about: { bg: "За нас", en: "About" },
  // ...
};

// Helper function
export function tr(key: string, locale: Locale): string {
  return t[key]?.[locale] ?? key;  // falls back to key if missing
}
```

### Key naming convention

Keys are grouped by area using prefixes:

| Prefix | Area | Example |
| --- | --- | --- |
| `nav_` | Navigation | `nav_home`, `nav_events` |
| `btn_` | Buttons | `btn_register`, `btn_send` |
| `footer_` | Footer | `footer_tagline`, `footer_rights` |
| `hero_` | Hero section | `hero_badge`, `hero_cta_secondary` |
| `section_` | Section titles | `section_mission_title` |
| `step` | Steps (how it works) | `step1_title`, `step1_desc` |
| `form_` | Form labels & messages | `form_name`, `form_success` |
| `newsletter_` | Newsletter | `newsletter_title` |
| `date_label`, `location_label`, etc. | Misc labels | — |

**Rules:**
- Use `snake_case` for all keys
- Prefix with the area/section name
- Be descriptive — `form_register_for` is better than `frf`
- Group related keys together in the file

## Using Translations in Components

### In Server Components

```typescript
import { tr, type Locale } from "@/lib/i18n";

export default function AboutPage({ params }: { params: { locale: Locale } }) {
  const locale = params.locale ?? "bg";
  return (
    <h1>{tr("section_mission_title", locale)}</h1>
  );
}
```

### In Client Components

```typescript
"use client";
import { tr, type Locale } from "@/lib/i18n";
import { useLocale } from "@/lib/useLocale"; // to be created in Phase 1

export function NavButton({ locale }: { locale: Locale }) {
  return <button>{tr("btn_register", locale)}</button>;
}
```

## Locale State Management

The active locale is determined by (planned approach — to be implemented in Phase 1):

1. **Cookie** (`locale=bg|en`) — persists across sessions
2. **URL** — optional prefix (`/en/about`) for shareable links
3. **Default** — `bg` (Bulgarian) if no cookie/URL preference

### Language toggle

A toggle button in the navigation switches between BG and EN:

```text
[ БГ | EN ]  ← click to switch
```

The toggle:
- Sets the `locale` cookie
- Updates the `<html lang>` attribute
- Re-renders content in the new locale

## Adding New Translations

### Step-by-step

1. **Identify the string** you need to translate
2. **Choose a key name** following the naming convention (e.g., `services_theta_title`)
3. **Add to `lib/i18n.ts`:**

```typescript
services_theta_title: {
  bg: "Theta изцеление",
  en: "Theta Healing",
},
services_theta_desc: {
  bg: "Медитативна техника за енергийно изцеление...",
  en: "A meditation-based energy healing technique...",
},
```

4. **Use in your component:** `tr("services_theta_title", locale)`
5. **Verify both languages** render correctly

### Checklist for new strings

- [ ] Key follows `snake_case` and area prefix convention
- [ ] Bulgarian text is the source (written first)
- [ ] English translation is idiomatic (not literal)
- [ ] Key is placed in the correct section of the dictionary
- [ ] No hardcoded strings in components — always use `tr()`

## Long-Form Content

For longer content (blog posts, event descriptions, full page sections), storing everything in `i18n.ts` becomes unwieldy. The approach:

### Option A — Separate content files (recommended for launch)

```typescript
// lib/content/events.ts
export const events = [
  {
    slug: "theta-seminar-november",
    title: { bg: "Theta семинар — Ноември 2026", en: "Theta Seminar — November 2026" },
    description: { bg: "...", en: "..." },
    date: "2026-11-15",
    // ...
  },
];
```

### Option B — CMS (post-launch)

Migrate to Sanity, Payload, or another headless CMS with native i18n support. See [ROADMAP.md](../ROADMAP.md) backlog.

## Date & Number Formatting

Bulgarian and English use different date formats:

| Locale | Format | Example |
| --- | --- | --- |
| `bg` | `DD.MM.YYYY` | `10.11.2026` |
| `en` | `Nov 10, 2026` | `Nov 10, 2026` |

Use the `Intl` API for locale-aware formatting:

```typescript
new Intl.DateTimeFormat(locale === "bg" ? "bg-BG" : "en-US", {
  day: "numeric",
  month: "long",
  year: "numeric",
}).format(new Date(date));
```

## Common Pitfalls

| Pitfall | Solution |
| --- | --- |
| Hardcoding Bulgarian in JSX | Always use `tr(key, locale)` |
| Forgetting the English translation | Every key MUST have both `bg` and `en` |
| Literal translations | Translate meaning and tone, not word-for-word |
| Missing key fallback | `tr()` returns the key name if missing — check for this in dev |
| Mixing locale in URL and cookie | Decide on one source of truth (cookie for now) |
